What you are looking at

A support agent that investigates a complaint, quotes the policy, and stops before it spends money.

A customer writes in. The agent reads their order, return and payment, finds the policy section that applies, and writes a reply. If money should move, it does not move it — it hands a reviewer a proposal and waits. That pause is the whole point of the project.

Refunds waiting on you

The agent never pays a refund on its own. It writes down exactly what it wants to do and waits here. If anything about that proposal changes afterwards, your approval stops counting and it has to ask again.

The hardest case for any system that spends money: the payment provider takes the refund, then the connection drops before it can tell you. Retry blindly and you have paid twice. Break it here on purpose and see what happens.

Break the payment provider

Pretend the server crashed

On restart it asks the provider about every refund it was unsure of, using the same key it sent, and only then carries on. That order matters: money first, workflow second.

What each agent may touch

            

              Every agent gets the smallest set of tools that does its job. The one that reads
              your order cannot pay you; only the step after a human approval can. Notice that
              nothing takes a customer id — the agent cannot choose whose account to look at.
            

            

          


          

            
The policy book

            

              Written as plain documents with version numbers and dates. The agent quotes them
              by section, so you can always check the answer against the rule it used. Old
              versions stay readable but are never quoted.
